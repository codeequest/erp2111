# Administration IAM (Users, Roles, Permissions, Security) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the 501 skeletons of the Administration area with a complete identity-and-access module: invitation-based users, multi-role RBAC with a permission matrix, TOTP MFA, secure resets, sessions, immutable audit and a security overview.

**Architecture:** Extend the existing NestJS auth (approach A). Permissions remain code-defined in `packages/shared` and seeded; all rules live in pure, unit-tested functions (`access-policy.ts`, `permission-resolution.ts`, `password-policy.ts`, `totp.ts`) called by services that run each write in one Prisma transaction with its audit row. The web app adds admin screens built from a small shared admin UI kit in the existing Tailwind style.

**Tech Stack:** NestJS 11, Prisma 6 / PostgreSQL 17, argon2, Node `crypto`, nodemailer (new), qrcode (new), Jest + Supertest (new dev dep); Next.js 15 App Router, React 19, Tailwind 4, lucide-react.

**Spec:** `docs/superpowers/specs/2026-11-25-admin-iam-design.md` (read it first; section numbers below refer to it).

## Global Constraints

- Branch `feature/admin-iam` from `main`; one commit per task; `pnpm typecheck` and `pnpm test` green after every task.
- Permission codes: `module.resource.action`, regex `^[a-z]+\.[a-z]+\.[a-z_]+$`; the full admin list is spec §7.1.
- Every route has `@RequirePermissions(...)` or `@Public()`; no route deletes a user.
- Every sensitive write: one `prisma.$transaction` containing its `recordAudit(...)` call.
- Secrets at rest: tokens SHA-256 hashed; recovery codes argon2-hashed; TOTP secret AES-256-GCM with `MFA_ENCRYPTION_KEY` (32 bytes, base64). Never log, return or audit a password, token, secret or recovery code (except returning recovery codes once at enrolment and the otpauth URI during enrolment).
- Public routes never reveal whether an email exists (same response body and status).
- Defaults (`SecurityPolicy` row): password min 12, max 128, lockout 5 attempts / 15 min, invitation 72 h, reset 60 min, `requireMfaForPrivileged` true, access review 90 days, dormant 60 days, revoke sessions on reset true, breach API check false.
- TOTP: RFC 6238, SHA-1, 6 digits, 30 s step, accept ±1 step, reject a step ≤ `last_used_step`. 10 recovery codes, format `xxxxx-xxxxx` (lower-case base32 alphabet).
- Challenge token: JWT signed with `JWT_ACCESS_SECRET`, claim `purpose: 'login_challenge'`, 5 min TTL, carries `sub` and `pending: ('password_change'|'mfa_enroll'|'mfa')[]`.
- Rate limits: login 10 / 15 min per (ip, email); MFA verify 5 per challenge token; forgot-password 3 / hour per email and 10 / hour per IP; accept-invite and reset 10 / hour per IP.
- Lists: `pageSize` ∈ {10, 25, 50, 100}, default 25; bulk ≤ 200 ids.
- Links in emails use `WEB_ORIGIN` and carry the token in the URL fragment: `/reset-password#token=…`, `/accept-invite#token=…`, `/verify-email#token=…`.
- UI: English only, existing Tailwind visual language, CSS motion only (no framer-motion, no next-intl); every async view has skeleton, error, empty and success states.
- Role colour keys (fixed palette): `slate, blue, emerald, amber, rose, violet, cyan, orange`.

## Review Focus

1. **Two admins deactivating (or de-roling) each other at the same instant** — exactly one succeeds, the other gets 409 "would leave no active administrator". Test in Task 13 (`last admin survives concurrent removals`).
2. **Stale matrix or role save after a colleague changed the role** — 409 with nothing applied, UI asks to reload. Tests in Task 11 (`rejects stale version`) and Task 13.
3. **Email with different case / surrounding spaces** (`"  Bob@X.com "` vs `bob@x.com`) — treated as the same account: create returns 409, login succeeds, forgot-password targets the same user. Tests in Task 10 and Task 8.
4. **Expired temporary role** — permissions vanish at `expires_at` with no background job, and an expired Admin assignment does not count toward "last administrator". Tests in Task 4.
5. **Reset / invitation link used after the user was deactivated, or used twice** — rejected with the generic invalid-link error; deactivation voids outstanding tokens. Tests in Task 8 and Task 13.
